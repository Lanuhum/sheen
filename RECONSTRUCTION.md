# Реконструкция кода репозитория «Sheen»

Этот документ описывает результат анализа дерева: что представляет собой код,
как он устроен, как он эволюционировал (по каталогу `incoming/`), какие в нём
есть проблемы и что требуется для его проверки.

---

## 1. Обзор проекта

**Sheen** — быстрый **преднамеренно смещённый (biased)** процедурный рейтрейсер
для анимации, написанный на CUDA/C++. Философия (см. `README.md`): аналитические
примитивы вместо сеток, жёсткие тени, плоский BVH, скорость как первичный
параметр дизайна. Код пишется ИИ-ассистентом по дорожной карте; каждый «дроп»
(`incoming/stepN/`) переносится в дерево, компилируется, запускается и сверяется
по пикселям перед приёмкой. Лицензия — MIT. Целевое железо — GTX 1080 Ti (`sm_61`),
800×600, steady state.

### Ключевые типы (`types.h`)

```
Transform(48B) Ray(32B) HitRecord(48B) CameraData(64B) Material(32B)
Object(32B: type/material_id/param1/param2) Light(32B) Plane(32B)
SweepPoint(16B: position+radius) SweepStrand(32B: offset/count/material)
BVHNode(32B: bbox_min/bbox_max/left/right)   // из bvh.h
```

`Object.type`: 0 = сфера, 1 = плоскость (устарело, плоскости вынесены в
отдельный массив `Plane`), 2 = sphere_sweep (заглушка в `get_object_bounds`).
Листья BVH кодируются как `~index` (битовое дополнение); пряди живут в
**отдельном** дереве `strand_bvh_nodes`, чтобы не конфликтовать с индексами
объектов. В `HitRecord.object_id` отрицательные значения различают источник
хита: `-1-i` — плоскость, `-(idx+1)` — прядь.

### Алгоритм рендера

1. На пиксель — 4 субсемпла (углы четвертей пикселя), луч из камеры
   (`right*u + up*v + forward`, нормализация).
2. Трекдинг в три этапа: BVH сфер → BVH прядей → массив плоскостей
   (плоскости сознательно держатся вне дерева — см. раздел «Эволюция», шаг 4b).
3. Освещение: ambient + направленный diffuse + Blinn-Phong specular;
   тень — луч от точки + normal·0.002 к источнику, тот же трёхэтапный трекдинг.
4. Промах — градиентное небо. Выход — `float4` RGBA, хост конвертирует в PNG.

### Конусная математика (`intersect_cone_segment`)

Сегмент между двумя `SweepPoint` — точный конус (линейно меняющийся радиус).
Луч переводится в систему координат оси; решается квадратное уравнение
`A s² + B s + C = 0` от условия `|Q⊥ + s·D⊥|² = (r0 + k(v + s·u))²`, где
`k = Δr/L`. Корни фильтруются по `[t_min, t_max]` и по длине сегмента
`0 ≤ v + s·u ≤ L`; нормаль — `radial/r − k·axis`, развёрнутая против луча.
Торцевые сферы **убраны намеренно** (коммит HEAD: «remove end-cap spheres»).

## 3. Эволюция кода по `incoming/`

Дропы восстанавливают историю развития (git-история обрезана до одного
«grafted»-коммита, поэтому `incoming/` — фактически единственный архив):

- **step2** — базовый рендер: сфера + материалы + свет, линейный скан
  `intersect_scene`, ядро без AA, без плоскостей.
- **step3** — добавлены плоскости как `type==1` в общем массиве объектов,
  жёсткие тени (`is_in_shadow`, сдвиг 0.002 вдоль нормали против shadow acne),
  локальные функции `make_float3` (позже удалены — встроенный CUDA-конструктор).
- **step3final** — стабилизация типов: удалён `make_float3`, добавлен
  `operator*(float3,float3)`, комментарии приведены к финальному виду.
- **step4** — первый рабочий BVH: один массив узлов, плоскость внутри дерева
  с ограниченным боксом ±100. Это дало регресс: 7-рядная полоса неба на
  горизонте и ускорение лишь 2.3x (O(N)-скан всё равно искал плоскость).
- **HEAD (вне incoming/)** — финальная форма:
  - плоскости вынесены в отдельный массив `Plane[]`, проверяются только после
    промаха дерева → горизонт ровно на геометрической линии, ускорение 26x;
  - добавлены `sphere_sweep`-пряди: `SweepPoint/SweepStrand`, конусная
    интерсекция, **второе, отдельное BVH для прядей**;
  - исправлены конусы A/C (см. комментарий «ИСПРАВЛЕНО» в `intersect.h`);
  - включён 4x AA по умолчанию; тест расширен до 1000 сфер + 3 прядей;
  - `tools/bench.cu` сверяет изображения pixel-by-pixel (0 расхождений).

Метрики README (GTX 1080 Ti): linear 10.4/55.7 мс, BVH 0.40/1.95 мс (no AA / 4x AA).

## 4. Сборка и окружение

Требуется: Linux, CUDA Toolkit 12.x, CMake 3.25+. Два бэкенда:

- **clang++** (по умолчанию): `--cuda-path=/usr --no-offload-new-driver`,
  потому что nvcc 12.9 не разбирает заголовки GCC 15 libstdc++;
- **nvcc** (`-DSHEEN_BACKEND=nvcc`): использует заглушки из `shim/`
  (`bits/c++config.h` переопределяет `_GLIBCXX_USE_BUILTIN_TRAIT`,
  `type_traits`-шим) и `-Wno-deprecated-gpu-targets`.

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j && ./build/sphere_test
```

⚠️ **В текущем контейнере проверить сборку невозможно**: нет ни `clang++`,
ни `nvcc`, ни `libcudart`, ни GPU (`nvidia-smi` отсутствует). Все выводы ниже
получены статическим анализом. Для верификации нужен хост с CUDA 12.x.

## 5. Выявленные проблемы реконструкции

При разборе обнаружены конкретные дефекты/риски, отсортированные по важности:

1. **`__host__`-код включает `__device__`-функции.** `GPU_DEVICE inline` в
   `intersect.h` — это чистый `__device__`, но `scene.h` вызывает
   `normalize()` из `add_directional_light` (хост), а `bvh.h` —
   `fminf/fmaxf` в CPU-рекурсии. Компилируется только потому, что clang
   ослабляет проверки `__host__`-вызовов `__device__`-функций; **nvcc-бэкенд,
   скорее всего, падает**. Чистое решение — `GPU_HOST_DEVICE` для этих
   хелперов или отдельные host-версии.
2. **Неинициализированный `HitRecord` при промахе.** `rec.hit` никогда не
   сбрасывается в 0; все `temp_rec`/`shadow_rec` — мусор со стека. Сейчас
   безопасно по счастливым путям, но `hit` как поле мёртв и вводит в заблуждение.
3. **`intersect_aabb` делит на ноль** при нулевой компоненте направления
   (`1.0f/0.0f = inf`); NaN-случай `0·inf` даёт ложные промахи для осевых
   лучей. Классика требует epsilon-защиты или signs-подхода.
4. **Переполнение стека BVH-обхода.** `int stack[64]` при худшем случае
   ~2·depth; 1000 сфер → глубина ≤10, ок; но «гребневидные» (comb) деревья
   >2^32 листьев или вырожденные распределения теоретически опасны. Стоит
   добавить assert или push двух детей в правильном порядке (near-first).
5. **`get_object_bounds` для `type==2` — заглушка `{0,0,0}`** (сам помечена
   в коде как «Пока заглушка»). Если в `objects` когда-нибудь окажется
   прядь, её бокс схлопнется в точку и дерево станет неверным. Сейчас
   пряди идут мимо этого пути — но ловушка живая.
6. **Расхождение бенчмарка с основной сценой.** В `bench.cu` материал
   оранжевых прядей указан как id 3 («orange material (id 3)»), хотя id 3 —
   серый пол; настоящий оранжевый — id 4 (в основном тесте именно так).
   Кроме того, `bench.cu` вообще не загружает на GPU данные прядей и
   передаёт `d_nodes` из пустого дерева при 0 объектах → UB-чтение
   `bvh_nodes[0]` в режиме BVH. Также дублированный комментарий (строки
   158–159) и неиспользуемый `horizon_probe`.
7. **Дублирование логики освещения**: `compute_lighting` в `render_kernel.cu`
   и инлайн-версия в `bench.cu` разошлись по сигнатурам; при изменении модели
   света придётся править оба места (или вынести в общий header).
8. **Пустые поля камеры**: `focal_length/sensor_width/shift_x/shift_y`
   никогда не заполняются и не используются — FOV захардкожен формулой
   юнит-плоскости в ядре. Планируемые «motion vectors / temporal accumulation»
   тоже ещё не имеют носителей в структурах.
9. **Мелочи стиля**: смешение `{...}`-инициализации и `make_float3` в
   истории дропов (в HEAD везде `{}`); `num_materials`/`num_objects`
   принимаются ядром, но не используются (материал берётся по `rec.material_id`
   без bounds-check); отсутствие обработки ошибок `cudaMalloc/cudaMemcpy`.
