# Sheen — план развития (закреплено 2026-10-18)

Состояние и передача дел: `HANDOFF.md` (что готово, что дальше, как собрать).

## Принцип
Одна истина — в памяти. Ноль прокладок. Всё, что можно не писать, — не пишем.
Скорость тут вторична (рендер кадра ≈ мс, вызов ≈ мкс): главное — чтобы нечему было
ломаться: ни файлов-двойников, ни парсеров, ни процессов, ни «двух истин».

## Цель
Концертный зал: сцена, софиты, прожекторы, люстры. Под неё и приоритеты:
свет → объёмные лучи → эмиссивные поверхности; текстуры и остальное — после.

## Закреплённые решения (не менять без явного запроса)
- **Blender 4.5 — навсегда.** Никаких миграций на 4.6+, пока жив проект. Решение пользователя.
- Ядро рендера (CUDA, `types.h`/`bvh.h`/`render_kernel.cu`) не трогаем — работает:
  800×600×4AA ≈ 1.7 мс на GTX 1080 Ti.
- Контракт между аддоном и рендерером — **бинарные буферы**, раскладка структур из `types.h`.
  Никакого JSON, никакого текстового формата сцены в пути рендера.
- CLI (`scene_render` + `.sheen`-файл) остаётся только как стенд для тестов/разработки.
  В путь рендера из Blender не входит.
- Компилятор CUDA — clang++ 20 (nvcc 12.9 несовместим с GCC 15; см. CMakeLists).
- **`sheen.so` собирается под Python конкретной сборки Blender** (сейчас 3.13).
  Сменится Python у Blender — модуль пересобрать; ctypes-фолбэк на
  `libsheen_c_api.so` остаётся как страховка.

## Аналитические примитивы (сделано 2026-10-18)
  1. **Суперэллипсоид** `(|x/a|^n+|y/b|^n+|z/c|^n)=1` — ✅ Выполнено (2026-10-18).
     `primitives/superellipsoid.h`: сэмплинг F по лучу + бисекция пересечения F=1
     (выпуклое тело), нормаль — аналитический градиент. Отдельный SE-BVH.
     Проверено: se_demo.sheen — шар (n=2), куб с фасками (n=6), почти куб (n=12),
     1.88 мс; C-API-тесты зелёные. Команда `se` в .sheen.
  2. **Общий CSG** — ✅ Выполнено (2026-10-18). Дерево операций union/intersection/
     difference над примитивами (сфера, суперэллипсоид). `CSGNode`, `integrator/csg.h`
     (интервалы входа/выхода, рекурсивный обход, merge по операциям),
     команды `csg_begin/csg_leaf/csg_end` в .sheen. Проверено: полая коробка с
     дверным проёмом (difference(куб, union(полость, дверь))). Потребовалось:
     cudaDeviceSetLimit(StackSize) для рекурсии; se_intervals с сужением до AABB
     и поддержкой старта внутри тела. Комната с дверями/окнами — теперь обычное дерево.
  3. **Lathe (тело вращения профиля)** — ✅ Выполнено (2026-10-18).
     `primitives/lathe.h`: профиль (y, radius) → цепочка конических сегментов
     через переиспользование intersect_cone_segment; отдельный Lathe-BVH.
     Команда `lathe cx cy cz mat n y r ...` в .sheen. Проверено: ваза
     (7-точечный профиль) рендерится с тенью, 1.55 мс 500×400.
  4. **Prism (экструзия профиля)** — ✅ Выполнено (2026-10-18). Семантика
     POV-Ray: 2D-профиль в XZ, экструзия по Y; под-контуры закрываются повтором
     первой точки, дырки по чётности наложений (where an even number overlaps).
     Крышки по Y + вертикальные стены linear_sweep. Команда `prism` в .sheen.
     Проверено: 3D-текст «HF» золотыми буквами на полу (3.87 мс 640×480).
   5. **Bezier_spline для prism/lathe** — ✅ Выполнено (2026-10-18).
      Кубические кривые Безье тесселируются на host-стороне ДО попадания
      точек в lathe_points/prism_points (принцип: примитив остаётся
      «контур+высота», CUDA-ядро и бинарный контракт не меняются).
      Команды `lathe_bezier` и `prism_bezier` в .sheen: контрольные точки
      профиля группами по 4 (одна группа = один кубик от точки 0 до точки 3,
      кривая непрерывна); `prism_bezier` замыкает контур повтором первой
      точки (как и prism). Параметр `subdiv` — число отрезков на сегмент
      кубика (дефолтное тесселирование считается в парсере). Проверено:
      плавная красная капля (prism_bezier, 2.86 мс 640×480) и глазурованная
      синяя ваза (lathe_bezier, 7.08 мс 500×400), без артефактов.
  6. **HF из карты высот (grayscale) — «утёс по которому идёт персонаж»** —
      ✅ Выполнено (2026-10-18). HeightField теперь умеет брать высоту НЕ из
      процедурного fBm, а из grayscale-изображения (1 байт/пиксель, bilinear).
      Одна картинка — единая истина: Blender строит из неё grid+displace
      превью-меш (видишь во вьюпорте, ориентируешь персонажа), а CUDA рендерит
      ту же карту аналитически (HeightField.image/img_w/img_h, семпл в hf_eval).
      Правка контракта (types.h/sheen_flat.h/c_api_contract.py, HeightField
      48→64 байта, поле image+img_w+img_h), ядро трассировки и render_kernel
      НЕ менялись (обход BVH прежний, карта семплится в самом примитиве).
      Канал: CLI `hf_image cx cy cz sx sz h file.pgm mat` (grayscale P5);
      мост `engine.py` + оператор SHEEN_OT_AddHeightField (файловый менеджер →
      Image + grid + displace + custom-props sheen_hf_*), рендер с той же карты.
      Проверено: утёс с плато и клифом из 256×256 PGM, 3.89–4.98 мс 640×480;
      c_api_test/sizes/sphere_test зелёные.
      Правка 2026-10-18: превью-сетка больше не уходит в рендер треугольниками
      (иначе двойная поверхность), модификатор Displace переведён на UV +
      Non-Color — карта в вьюпорте и аналитическая поверхность совпадают
      (средняя ошибка по высоте 0.03 при height=1.2).
  Далее: water_level-прорези в HF, скрипка/гитара из патчей + sweeps-струн.

## Свет: Point / Spot / Area (2026-10-18)

- `Light` расширен до 96 байт: `position`, `u_axis`/`v_axis`, `radius`,
  `angle`, `blend`. Типы: 0 — SUN, 1 — POINT, 2 — AREA, 3 — SPOT.
- Ядро: затухание `P/(4πd²)` для локальных источников; конус прожектора
  (`spot_size/2` + `spot_blend`); area светит с одной стороны
  (нормаль `cross(u,v)`); мягкая тень по `shadow_soft_size` — точка выборки
  сдвигается по диску, выборка на каждый AA-сэмпл (растёт вместе с AA).
- Мост: каждое поле берётся из свойств объекта; неизвестный тип пропускается
  с сообщением; нет источников — нет света (только `0.1·albedo` и небо).
- Проверено: пустая сцена — пол 0.31 (только ambient); дефолтная Point 1000 Вт
  — куб 0.91 (было 0.31 при Sun-only); spot — внутри конуса 1.0, снаружи 0.31;
  area 4×1 м — 75 промежуточных пикселей в полутени; CLI `lights_demo.sheen`
  12.4 мс; смоук зелёный.
- Приближения: area считается как `P/(4πd²)·cos`, а не через яркость и площадь;
  форма DISK/ELLIPSE аппроксимируется прямоугольником; угол солнца (мягкость
  тени) пока не используется.

Далее: объёмные лучи, эмиссивные поверхности, gobo-текстуры на прожекторах.

## Поток света у прожектора (2026-10-18)

- В `Light` добавлено `beam` (0 — выключено, размер структуры не изменился:
  место взято из выравнивания). Управление — свойство `Light → Sheen Beam`,
  панель появляется только у Spot и только при движке Sheen.
- Реализация — аддитивный конус по 6 сэмплам вдоль луча, **без теневых лучей**.
  Яркость гасится первой поверхностью (`rec.t`), поэтому геометрия перед
  конусом перекрывает луч; плотность `beam·P·1e-3/(1+0.25d²)`, край — по
  `spot_blend`, длина интегрирования ограничена 30 единицами.
- Цена: 640×480, два прожектора — +1.4 мс (12.5 против 11.1 мс);
  1920×1080 — +17 мс (73 против 56 мс). Сцена без `beam` платит ноль:
  ветка отсекается по `beam <= 0`.
- Проверено: кадр `lights_demo.sheen`, прирост до 39/255, выжженных пикселей 15
  (до калибровки упиралось в 255), смоук зелёный.

Далее: gobo-текстуры, фотоны (каустика).

## Тени внутри объёма луча (2026-10-19)

- Марш объёма получил теневой луч **на каждый шаг**: из точки шага к центру
  лампы (при `radius > 0` точка выборки сдвигается по диску — та же мягкая
  тень, что у поверхности). Если источник закрыт, шаг не даёт вклада —
  геометрия внутри конуса вырезает тёмные полосы.
- Стекло для теневого луча прозрачно, как и на поверхности: до трёх граней,
  остаток длины уменьшается на каждой грани (за свет не уходит).
- Цена: только для пикселей внутри конуса, по одному лучу на шаг.
  `scenes/beam_shadow.sheen`, AA 4: 640×480 — 2.56 → 3.21 мс (+0.65 мс);
  1920×1080 — 20.5 → 23.0 мс (+2.4 мс). В демо конус занимает ~4% кадра,
  поэтому вклад скромный; сцена, залитая лучом, заплатит пропорционально.
- При `beam <= 0` ветка не выполняется: кадр побитово совпадает со старым
  ядром, время то же (2.47 против 2.50 мс).
- Проверено: `scenes/beam_shadow.sheen` — щит у лампы и колонна в луче;
  13 977 пикселей (4.55% кадра) стали темнее, максимум 149/255, средняя
  яркость в тени 117.5 → 66.0. `media_room.sheen` и `lights_demo.sheen`
  побитово не изменились; c_api_test/sizes/sphere_test/mesh_test и смоук
  Blender (9/9) зелёные.
- Ограничения: тень берётся в 6 точках вдоль луча — на низком AA граница
  полутени ступенчатая; пропускание стекла не ослабляется (как и у теней
  на поверхности); среда в самом луче по-прежнему не ослабляет поток
  (это аддитивная аппроксимация, не полноценный in-scattering).

## Рассеивающая среда (2026-10-18, POV-Ray 2.3.7.6)

- В контракт добавлены `Medium` (48 байт) и `media/num_media` в сцене;
  у света `flags` bit0 — взаимодействие со средой (`media_interaction`).
- Ядро: марш внутри AABB среды, однократное рассеяние, изотропная фаза,
  теневой луч на каждый источник (окно/решётка дают лучи). Ослабление
  поверхности и фона — `exp(-sigma_t·d)`. `samples` — шагов вдоль луча,
  цена линейна; большие боксы запрещены самой логикой (как в POV-Ray).
- CLI: `media cx cy cz hx hy hz sr sg sb sigma_t samples`,
  `fill_light ...` (свет, не взаимодействующий со средой),
  `se_csg ...` — суперэллипсоид только для CSG (стены с проёмами).
- Blender: объект-меш с `sheen_media` задаёт объём по своему AABB
  (Scatter/Extinction/Steps в панели Sheen Medium); у лампы — флажок
  «Sheen Light → Light in media». Контейнер в рендер не попадает.
- Замеры: демо `scenes/media_room.sheen` 640×480, AA 4, 32 шага —
  212 мс против 17.7 мс без среды; через мост Blender — 51k пикселей
  разницы. Формула сцены и настройки подобраны под «луч в воздухе».

Границы: только однократное рассеяние (нет многократного), нет фотонов
и отражений — поэтому 2.3.7.7 (отражающий пол + photon mapping) пока
не воспроизводится. Площадные источники в среде считаются по центру.

## Отражение глубины 1 (2026-10-19, к POV-Ray 2.3.7.7)

- `Material.reflect` занял прежний padding — размер 64 байта не изменился;
  мост читает `Material → Sheen Material → Reflect`; CLI: `reflect <mat> <value>`.
- Ядро: после первичного цвета и среды бросается зеркальный вторичный луч;
  освещение считается тем же `compute_lighting`, среда маршится и по
  отражённому лучу — поэтому в полу отражается и луч в воздухе. Глубина 1,
  без рекурсии; марш среды вынесен в `media_march`.
- Стек: после удвоения инлайна ядро стало изредка падать в illegal memory
  access — `cudaLimitStackSize` поднят с 4 КБ до 16 КБ, 10/10 прогонов чистые.
- Демо `scenes/media_room.sheen`: пол `reflect 0.55`, окно с переплётом 2×2.
  640×480, AA 4: 475 мс (луч + отражение), 344 мс (только луч), 42 мс
  (только отражение). Отражение меняет 138 757 пикселей, максимум 118/255.
- Артефакт на стыке переплёта (разрыв в отражении) починен 2026-10-19:
  причина была не в отражении, а в CSG — union просто склеивал интервалы
  без слияния перекрытий (см. раздел ниже).
- Фотонных карт нет: это однократное зеркало, а не photon mapping POV-Ray.

## Мягкое солнце и починка union (2026-10-19)

- **Мягкое солнце.** `Light.angle` у SUN — угловой радиус: мост берёт
  `data.angle` (полный диаметр в Blender) и делит пополам. Направление на
  солнце джиттерится в конусе (`sun_dir`), используется и в затенении, и в
  марше среды — края лучей и теней перестают быть «векторными».
  CLI: `sun_angle <радианы>` для последнего источника. При angle = 0
  поведение прежнее, жёсткое.
- **Union в CSG.** Была заглушка: интервалы A и B просто дописывались в
  список, без слияния перекрытий. Из-за этого на пересечении двух стоек
  окна появлялся разрыв (в прямом виде и в отражении). Теперь union
  сортирует интервалы по входу и сливает перекрывающиеся — стык сплошной,
  сцена-обходка (difference вместо union) больше не нужна.
- Проверено: стык переплёта без щели (визуально), смоук 9/9,
  `scenes/media_room.sheen` — 490 мс (луч + отражение), угол солнца из
  Blender доходит как 0.0873 рад при 10°.

## Текстуры материалов (2026-10-19)

- Мост выгружает Image Texture, подключённую к Base Color у Principled:
  пиксели (линейные float RGBA от Blender) квантуются в RGB-байты,
  индекс кладётся в `Material.texture_id`. В ядре и контракте это было
  готово (`TextureRef`, `sample_texture`, UV в треугольниках) — не хватало
  только выгрузки из Blender.
- Проверено: шахматка 8×8 на плоскости — std 52.7 против 6.2 у плоского
  цвета, клетки 247/143; `textures: 1, texture_id: 0`; смоук 9/9.
- Ограничения: одна текстура на материал, только Base Color, без
  Mapping/UV-transform и без mip-фильтрации (билинейно с повтором).

## Gobo на прожекторе (2026-10-19)

- У света появился `texture_id` — занял padding, `Light` остался 96 байт.
- Ядро: у SPOT направление на точку проецируется в UV конуса

- Проверено: шахматка 4×4 на полу — std 54.4 против 3.4 без gobo, граница

## Эмиссивные материалы — видимые источники (2026-10-19)

- `Material` 80 → 96 байт: `emission_color` (линейный цвет) + `emission`
  (сила). Правка синхронно в `types.h`, `sheen_flat.h`, `c_api_contract.py`
  и в статическом тесте размеров.
- Ядро: к цвету поверхности до затенения прибавляется
  `emission_color · emission`. Свечение не зависит от источников и не
  затеняется; вторичный отражённый луч идёт через тот же `compute_lighting`,
  поэтому лампа видна и в отражении (глубина 1), и за стеклом.
- Blender: у Principled читаются **Emission Color** и **Emission Strength**
  (дефолт 0); отдельного свойства аддона не нужно. CLI:
  `emit <материал> r g b strength`.
- Проверено: `scenes/emission_demo.sheen` — люстра из трёх шаров-ламп в
  тёмном зале с полу-зеркальным полом. С `emit ... 3.0` центры ламп
  (255,255,255), без свечения — (17,18,21); отражение в полу (255,239,188)
  против (41,43,50); меняется 1624 пикселя. 640×480 AA 4 — 16.7 мс.
  `media_room.sheen` и `lights_demo.sheen` побитово не изменились,
  смоук 9/9, c_api_test/sizes/sphere_test/mesh_test зелёные.
- **Попутно починен старый баг**: `Scene::add_material` не инициализировал
  `reflect`, `transmission`, `ior` — они читались как мусор со стека.
  Из-за этого кадр зависел от раскладки кучи: при пути вывода в `resolution`
  длиннее 15 символов из сцены пропадал пол. Теперь `Material = {}` и явные
  дефолты; кадр не зависит от длины пути.
- Ограничения: свечение — только цвет и сила, текстура в Emission Color
  игнорируется; эмиссивная поверхность **не освещает** сцену (нет GI и
  sampling эмиссии как источника) — это видимое тело, а не лампа; сила > 1
  упирается в 255 при записи sRGB; на теневые лучи эмиссия не влияет.

## Карта свойств материала — жилы и слюда (2026-10-20)

- `Material.mask_id` занял хвост структуры — `Material` остался 96 байт.
  Одна карта на материал: **R — transmission, G — IOR−1, B — roughness**.
  Смысл — свойства жилы (прозрачность, показатель преломления, глянец)
  выводятся из одной маски, поэтому цвет, прозрачность и блеск совпадают
  по построению, а не подбираются отдельно.
- Ядро: B переводит roughness в показатель Блинна
  (`2/r⁴−2`, та же формула, что в мосте); R умножает скалярный
  `transmission` материала (в шейдинге, в проходе стекла и на теневых лучах —
  стекло для тени по-прежнему прозрачно); G даёт IOR `1.0 + G`
  (слюда: 0.6 → 1.6). Нет маски (`mask_id < 0`) — всё работает по скалярам,
  лишних сэмплов нет.
- CLI: `mask=<индекс>` у `material`; Blender: Material → Sheen Material →
  **Mask** (Image, линейные пиксели → RGB-байты, как albedo).
- **Кубы получили UV.** Раньше `add_cube` строил треугольники без UV, и любая
  текстура на кубе вырождалась в один тексель. Теперь у каждой грани своя
  развёртка 0..1 (X-грани: z/y, Y-грани: x/z, Z-грани: x/y).
- Демо `scenes/granite.sheen` + `scenes/textures/granite_{albedo,mask}.ppm`
  (512×512, сгенерированы офлайн): гранитный блок, золотая жила в albedo и
  тонкий прожилок слюды, у которого R маски даёт прозрачность, а G — IOR 1.6.
  Проверено: с маской и без неё различаются 32 149 пикселей (до 175/255) —
  это и слюда, и глянец золота против камня. 800×600 AA 4 — 6.5 мс.
- Ограничения: маска одна (нет отдельных карт для нормалей и metallic),
  нормалей в контракте пока нет вообще; у аналитических примитивов (plane,
  sphere, lathe) UV либо нулевые, либо условные — маска и albedo на них
  работают только там, где UV задан примитивом; мип-фильтрации нет.

## Карты нормалей и мипы (2026-10-20)

- `Material` 96 → 112 байт: `normal_id` (92) и `normal_strength` (96).
  `TextureRef._pad` стал `mips` — размер референса не изменился.
- **Мипы** строятся на хосте box-фильтром 2×2 в тот же буфер: уровни идут
  подряд, каждый следующий — половина предыдущего. Ядро считает смещение
  уровня по width/height, поэтому отдельных указателей не нужно. Работает
  в обоих путях (CLI и C-API от Blender).
- **LOD** — по footprint: `uv_fp` = размер пикселя в UV. Угловой размер
  пикселя берётся из focal_length, умножается на расстояние до попадания;
  для мешей — ещё на плотность UV треугольника (по длинам рёбер и UV).
  У HF/SE UV заданы в мировых единицах, плотность 1. Уровень =
  `log2(uv_fp · width)`.
- **Нормали**: RGB → [-1,1], XY умножаются на `normal_strength`, базис
  строится от геометрической нормали. Мост читает Normal Map → Image Texture
  и Strength у входа Normal у Principled. CLI: `normal=<tex>`, `nstr=<сила>`.
- Демо `scenes/granite.sheen` + `granite_normal.ppm` (из albedo, 512×512):
  с нормалями и без различаются 15 293 пикселя (до 94/255), std в кубе
  27.8 против 25.1. 800×600 AA 4: 6.0–7.2 → 7.1–7.3 мс.
  compute-sanitizer memcheck: 0 ошибок (выборка мипов в границах буфера).
- Тангенциальный базис для нормалей берётся из UV треугольника (dp/du и
  dp/dv из рёбер), у аналитических примитивов — произвольный от нормали.
  На кубе с блочной развёрткой базис совпал со старым (0 пикселей разницы),
  поэтому проверка на изотропном граните ничего не доказывает; формула
  стандартная, memcheck чист.
- Ограничения: у plane/sphere UV нет, мипы там работают по допущению
  «1 UV = 1 единица мира»; LOD без анизотропной фильтрации.

## M2 — движок в Blender (2026-10-18)

- **Сборка и установка одной командой.** Цель CMake `sheen` (Python-модуль,
  раньше собирался руками) + `cmake --install build`: аддон целиком
  (`*.py` + `libsheen_c_api.so` + `sheen.so`) кладётся в
  `~/.config/blender/4.5/scripts/addons/sheen_render`. Поиск библиотек по
  каталогам сборки удалён — файлы лежат рядом с `engine.py`, для разработки
  есть `SHEEN_LIB`.
- **Настоящий RenderEngine** (`bl_idname = "SHEEN"`): F12, Render Animation,
  Output/Color Management работают штатно. Кадр рендерится во временный PNG,
  пиксели отдаются в результат; панель настроек — в Render Properties.
- **Цвет.** Ядро отдаёт display-referred sRGB, поэтому движок переключает
  View Transform на **Raw** — иначе Blender применяет вторую трансформацию.
  Совпадение с прямым рендером: отличие ≤ 1/255.
- **Мост (M1).** Материалы по слотам + Principled, UV, нормали в мире,
  `csg_root = -1`, sRGB при записи, AA из слайдера, пути и Resolution %.

Далее: текстуры из нод (пиксели `Image` → `TextureRef`), точечные/площадные
лампы, World-фон, анизотропные волосы.

## Решения (не менять без явного запроса)
- **Типы кривых — только из Blender (Poly/Bezier/NURBS), а не из POV-Ray.**
  POV-Ray — образец возможностей аналитических примитивов, но НЕ источник
  типов сплайнов. Профили для prism/lathe приходят из Curve-объектов Blender
  (BEZIER/POLY/NURBS, use_cyclic_u, splines[]), мост читает их через bpy.
- **Geometry-пропсы 2D-кривых Blender определяют объём призмы.**
  Для Curve с dimensions='2D': extrude → y_min/y_max призмы; fill_mode и
  use_fill_caps → заполнение крышек; offset → смещение контура до построения
  примитива; bevel_depth + bevel_resolution → скругление рёбер (фаска).
  Все пропсы применяются в мосте (bpy), примитив остаётся «контур+высота».
- **Этап 4 — (не сейчас) RE_engine.** C-движок с настоящими dev-хедерами Blender,
  Python из цикла полностью. Нужен собранный Blender, фиксация ABI, GPL-нюанс при
  линковке. Выигрыша по скорости нет — только сложность. Отложен осознанно.

## Мера успеха
Кадр из Blender: bpy-объекты → буферы в памяти → libsheen на GPU → PNG.
Ни одного файла-прокладки, ни одного процесса, ни одного парсера в пути рендера.
